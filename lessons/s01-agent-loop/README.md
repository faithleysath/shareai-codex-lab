# s01-agent-loop

这是 ShareAI 教程第一节 `s01` 的 Bun + TypeScript 实践版本。

这一课我们没有开放危险的 shell，而是实现了一个更安全、更容易观察原理的例子：

- 模型只能调用一个本地工具 `list_directory`
- 这个工具只能读取固定根目录内部的内容
- 每次只返回一层目录内容
- agent 必须通过循环多次调用工具，才能拼出完整 tree

这正好能把 `agent loop` 的本质看得很清楚：模型提工具请求，本地代码执行工具，再把结果喂回模型继续思考。

## 原理拆解

第一课最重要的目标，不是把功能做复杂，而是把 agent 的最小闭环看清楚。

这一课里，系统只有三样关键东西：

- 一个模型调用
- 一个本地工具 `list_directory`
- 一个 while/for 风格的循环

只要把这三样东西串起来，你就已经拥有了最小可用的 agent。

### 这节课到底在学什么

这一课不是在学“怎么列目录”，而是在学：

- 模型什么时候要工具
- 本地代码怎么执行工具
- 工具结果怎么回到模型上下文里
- 模型怎么在多轮里逐步完成任务

目录树这个例子只是载体。它之所以适合第一课，是因为：

- 目标很直观
- 工具返回值很好观察
- 一层目录不够，就天然需要多轮循环

### 这节课的完整链路

可以把整个程序理解成下面这条最小链路：

1. 启动程序，读取 `.env`。
2. 创建 `OpenAI` 客户端。
3. 创建一个安全工具 `list_directory`。
4. 组装初始消息：
   - system prompt
   - user prompt
5. 把消息和工具 schema 一起发给模型。
6. 如果模型返回 `tool_calls`，本地代码执行对应工具。
7. 把工具结果包装成新的 `tool` message，追加回消息历史。
8. 再次调用模型。
9. 重复这个过程，直到模型返回普通文本答案而不是工具调用。

这就是第一课的 agent loop。

### 为什么这个例子天然需要循环

因为 `list_directory` 有一个刻意的限制：

- 它每次只返回一层目录内容
- 它不会递归返回整个目录树

所以如果模型想拿到完整 tree，就不能靠一次工具调用完成，而必须这样推进：

1. 先看根目录
2. 发现哪些是子目录
3. 再分别查看这些子目录
4. 一直重复到没有新的子目录需要展开

这正是 agent loop 的典型形态：先拿一点信息，再决定下一步。

### `list_directory` 做了什么

这个工具不是简单跑一条 shell 命令，而是本地代码里的一个受限能力。

它做了几件事：

- 接收一个相对路径 `relative_path`
- 强制这个路径必须在固定根目录内
- 只读取该目录下一层内容
- 返回结构化 JSON 和一个便于人读的 tree 预览

也就是说，模型虽然能“探索目录”，但它的能力边界是我们本地代码定义出来的。

### 为什么不用 bash

第一课故意不用 bash，是因为 shell 的能力太大了：

- 能读任意文件
- 能执行命令
- 容易让“工具能力边界”变得不清晰

而 `list_directory` 这个工具非常收敛：

- 只能读目录
- 只能读固定根目录内
- 只能读一层

这会让你更容易看清 agent 的真正工作方式，而不是被 shell 的巨大能力掩盖掉。

### 为什么第一轮要强制用工具

代码里有一行很关键：

```ts
tool_choice: round === 1 ? "required" : "auto"
```

它的意思是：

- 第一轮：必须先调工具
- 后面几轮：模型自己决定是否继续调工具

这样设计是为了教学稳定性。

如果第一轮就用 `auto`，有些模型可能会直接“猜一个目录树”，而不是先去拿真实信息。第一轮强制工具调用后，loop 就一定能启动起来，你能明确看到：

- 模型请求工具
- 本地执行工具
- 工具结果回流

后面再改成 `auto`，模型就可以在信息足够时自然停下来。

### `parallel_tool_calls` 在第一课的意义

代码里还设置了：

```ts
parallel_tool_calls: false
```

它表达的是一种偏好：

- 希望模型一轮里不要一次性发很多工具调用
- 更偏向一步一步推进

不过它并不是绝对硬约束。不同 OpenAI 兼容服务可能仍然会在某些轮次返回多个 tool call。

所以第一课里你可以把它理解成：

- 我们希望 agent 行为更线性、更容易观察
- 但兼容服务不一定完全严格遵守

### 为什么第一课还不需要 dispatch map

因为第一课只有一个工具：

- `list_directory`

只有一个工具时，代码里直接判断工具名就够了，不需要专门搞一层工具注册表。

所以第一课的重点是：

- 先把 loop 看明白
- 不急着把工程结构做复杂

dispatch map 是第二课才开始真正值得引入的东西。

### 第一课和后面两课的关系

第一课解决的问题是：

- agent 最小闭环长什么样

第二课才会继续回答：

- 如果工具变多了怎么办

第三课才会继续回答：

- 如果任务变复杂了，怎么让 agent 记住计划

所以第一课可以理解成整个系列的地基。

## 这节课学到的核心

1. Agent loop 不神秘，本质就是“请求模型 -> 执行工具 -> 追加结果 -> 再请求模型”。
2. 工具越受限，越容易理解 agent 的行为边界。
3. 一层一层列目录这个例子非常适合学习，因为它天然需要多轮循环。
